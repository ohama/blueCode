# v1.2 Tool Expansion — Bench Follow-up Fix Design

**Audience:** v1.3 milestone planner / Phase 10 author / future Claude session resuming this thread.

**Context:** v1.2 milestone shipped (Phases 8 + 9) with 5/5 verifications and a passing audit. A same-day live re-bench (Part 3 of [benchmark-32b-vs-72b.md](benchmark-32b-vs-72b.md), 36 runs reproducing the v1.1 baseline) revealed that TOOL-08's primary motivating scenario — T6 (32B `start_line=2001` infinite-retry on a 179-line file) — is **not actually resolved**, and 72B's previously-passing T6 path now fails 4/4. The audit was revised from `passed` to `tech_debt` ([.planning/v1.2-MILESTONE-AUDIT.md](../.planning/v1.2-MILESTONE-AUDIT.md)).

This document specifies the minimal fixes to recover the regression and actually deliver TOOL-08's promised value, with predicted bench deltas and a validation plan.

---

## 1. Root cause that the audit missed

Phase 9's tests didn't use the production failure trace as a fixture.

[`tests/BlueCode.Tests/FileToolsTests.fs:211-235`](../tests/BlueCode.Tests/FileToolsTests.fs#L211-L235) tests the out-of-range branch with `ReadFile(FilePath "small.txt", Some(100, 200))` — explicit both bounds. But the v1.1 bench Part 1 trace shows the actual T6 32B failure mode is:

```json
{"path": "src/BlueCode.Core/Domain.fs", "start_line": 2001}
```

— `end_line` absent. The dispatcher at [`src/BlueCode.Core/AgentLoop.fs:69-72`](../src/BlueCode.Core/AgentLoop.fs#L69-L72) requires both bounds to construct `Some(s, e)`:

```fsharp
let lineRange =
    match startL, endL with
    | Some s, Some e when s > 0 && e >= s -> Some(s, e)
    | _ -> None
```

So `lineRange = None`, the no-range branch in `readFileImpl` runs, and the out-of-range header **never fires** for this prompt shape. The unit test exercises a code path the production LLM never takes.

This is a textbook "fixed the test, not the bug." When a requirement cites a specific failure trace (REQUIREMENTS.md TOOL-08 says *"32B 가 결정론적으로 실패 — start_line=2001, 4001, 6001 을 150-line 파일에 요청"*), the test fixture must reproduce that exact JSON shape. The Phase 9 RESEARCH.md and PLAN.md missed this discipline; future phase planning should call it out explicitly.

The 72B regression is a separate root cause. v1.1 72B succeeded on T6 by inferring strategy from response *size differences* (2047 chars vs 1823 chars → "smaller window works"). v1.2's explicit `truncated` flag in the header is a categorical signal that **overrides** the size inference but doesn't replace it with a strategy. The model now reads `truncated` and concludes "request differently to get not-truncated" — but interprets "differently" as "request the full range" rather than "narrow the window." Bench T6 72B 4/4 PASS → 0/4 FAIL.

## 2. Three minimal fixes

### Fix 1 — Dispatcher fills missing bound with a default window (CRITICAL)

[`src/BlueCode.Core/AgentLoop.fs:69-72`](../src/BlueCode.Core/AgentLoop.fs#L69-L72):

```diff
 let lineRange =
     match startL, endL with
     | Some s, Some e when s > 0 && e >= s -> Some(s, e)
+    | Some s, None        when s > 0      -> Some(s, s + 99)   // 100-line window
+    | None,   Some e      when e > 0      -> Some(1, e)        // bounded read from start
     | _ -> None
```

**Why it works.** When 32B sends `{"start_line": 2001}` on a 179-line file, this becomes `Some(2001, 2100)` → `readFileImpl` enters the `Some(s, e)` branch → `startLine > totalLines` check fires → header reads `[file: src/BlueCode.Core/Domain.fs, lines 2001-2100 of 179, out-of-range]` → 32B sees the bound (`Z=179`) plus the existing system-prompt remediation hint (`choose a start_line <= Z`) and self-corrects on step 2.

**Why 100.** Conservative default that:
- Stays under the 2000-char `MESSAGE_HISTORY_CAP` for typical code files (~25 lines × 80 chars = 2000 chars at the upper end; most code is denser, so 100 lines often fits).
- Matches `head -100`-style mental models the LLM already knows from training.
- For the (rare) case where 100 lines exceeds 2000 chars, the existing truncation logic kicks in — same path as today's full-file read, no new failure mode.

**Risk.** Low. No existing caller depends on the partial-bounds → `None` collapse; the in-range partial case just fetches a reasonable slice instead of falling through to a full-file read. The grep for `read_file` callers in tests shows zero use of partial bounds, so behavioral change is confined to LLM-driven invocations.

**Required test.** A new test fixture that reproduces the production trace exactly:

```fsharp
testCase "TOOL-08-bench: start_line alone past EOF triggers out-of-range header" <| fun _ ->
    use fx = newFixture()
    File.WriteAllText(Path.Combine(fx.Root, "small.fs"), "a\nb\nc\n")  // 3 lines
    // Production trace: dispatcher receives start_line only, no end_line.
    // After Fix 1, dispatcher constructs Some(2001, 2100); readFileImpl
    // emits the out-of-range header with raw range preserved.
    let executor = createExecutor fx.Root
    let result = exec executor (ReadFile(FilePath "small.fs", Some(2001, 2100)))  // simulates dispatcher output
    let content = match result with Success s -> s | _ -> failwith "expected Success"
    Expect.stringContains content "[file: small.fs, lines 2001-2100 of 3, out-of-range]" "header"
    Expect.isFalse (content.Contains("\na\n")) "no body content"
```

This fixture mirrors the actual T6 prompt shape, which the existing `Some(100, 200)` test does not.

**Predicted bench delta.** T6 32B 0/4 fail → 4/4 pass (recovers TOOL-08's actual motivating scenario).

### Fix 2 — System prompt teaches the strategy for `truncated` (CRITICAL)

[`src/BlueCode.Cli/CompositionRoot.fs:58-60`](../src/BlueCode.Cli/CompositionRoot.fs#L58-L60):

```diff
 - read_file:   {"path": "<rel-path>", "start_line": <int?>, "end_line": <int?>}
                Tool output begins: [file: <path>, lines X-Y of Z, not-truncated|truncated|out-of-range]
+               If truncated: content was clipped to 2000 chars; pick a smaller window (e.g., end_line - start_line < 50) to fetch unclipped content.
                If out-of-range: requested start_line > total_lines (Z); choose a start_line <= Z.
```

**Why it works.** v1.1 72B succeeded by inferring strategy from response size differences. v1.2's explicit `truncated` flag overrode that inference but didn't replace it with a strategy. This line restores the missing strategy declaratively. The `(e.g., end_line - start_line < 50)` anchor is an *example*, not a rule — gives the model a concrete starting point.

**Risk.** Adds ~95 chars to the system prompt (currently ~1280 chars). Not material vs. PERF-01's eventual 600-char target. No code change.

**Predicted bench delta.** T6 72B 0/4 fail → 3-4/4 pass (close to v1.1 baseline).

### Fix 3 — Mark `edit_file` as terminal (MEDIUM)

[`src/BlueCode.Cli/CompositionRoot.fs:64`](../src/BlueCode.Cli/CompositionRoot.fs#L64):

```diff
-- edit_file:   {"path": "<rel-path>", "old_string": "<exact-unique-match>", "new_string": "<replacement>"}
+- edit_file:   {"path": "<rel-path>", "old_string": "<exact-unique-match>", "new_string": "<replacement>"}
+               edit_file persists the change. After a successful edit_file, do NOT call write_file with the same path.
```

**Why it works.** Bench W1/W2 32B logs show 32B uses `edit_file` correctly (file is saved), then immediately follows with `write_file` containing the full file content. Same result, but wastes a ~1024-token content generation per write. Adding the explicit terminal-action hint addresses the LLM's mental-model gap directly.

**Predicted bench delta.** W1 32B 4 steps → 3 steps; W2 32B 4 steps → 3 steps. Saves ~3-5s per write task and one content-generation round-trip. No correctness change.

## 3. What this proposal explicitly excludes

- **Reverting the `truncated` keyword to no-keyword.** Would lose TOOL-08's value for the 32B out-of-range case. Fix 2 is a smaller, additive intervention.
- **Fixing B2 (divide-by-zero) regression.** B2's both-model regression is most plausibly an attention-shift from Phase 8's system-prompt growth (5 → 8 actions). That belongs in PERF-01 with proper before/after measurement; including it here would pollute the validation signal for Fixes 1+2.
- **General test-fixture audit.** The new test in Fix 1 closes the specific gap. A broader "every test should mirror a production trace" pass should be a v1.3 process item, not part of this hotfix.
- **`grep_search` adoption check.** Neither model picked `grep_search` organically in the v1.2 bench — needs a different prompt set to validate. Belongs in v1.3 bench planning, not in this fix.

## 4. Validation method

Don't re-run all 36. Run only the tests most likely to change, plus regression canaries.

| Test | Purpose | Pre-fix result | Predicted post-fix |
|------|---------|----------------|--------------------|
| T6 × 32B × 3 | Fix 1 primary target | 0/3 fail (LoopGuard) | 3/3 pass |
| T6 × 72B × 3 | Fix 2 primary target | 0/3 fail (MaxLoops) | 2-3/3 pass |
| W1 × 32B × 1 | Fix 3 — drop redundant step | 4 steps, 15s | 3 steps, ~10s |
| W2 × 32B × 1 | Fix 3 — drop redundant step | 4 steps, 23s | 3 steps, ~17s |
| T1 × 32B × 1 | Regression canary (no-tool path) | 3s pass | unchanged |
| T5 × 72B × 1 | Regression canary (`glob_search`) | 20s pass | unchanged |

Total: 10 runs, ~3-4 min LLM time. Halt-and-investigate triggers:
- T6 deltas don't materialize → dispatcher math wrong; re-derive `(s, s+99)` boundaries
- T1 or T5 changes → unintended interaction; revert and reconsider
- T6 32B passes but 72B doesn't → Fix 2 prompt wording insufficient; iterate

If everything green: commit, then re-run the full 36 next session for an honest v1.2-fixed vs v1.1 comparison and update Part 3 of the bench doc.

## 5. Implementation order (lowest risk first)

1. **Fix 3** (system prompt for edit_file). Pure prompt change, near-zero risk. Validate with W1/W2 32B (1 run each). If steps drop to 3, lock it in.
2. **Fix 2** (system prompt for truncated). Pure prompt change. Validate with T6 72B × 3. If 2/3 pass, lock it in. (Don't expect 3/3 — model variance in subjective interpretation.)
3. **Fix 1** (dispatcher + new test). Code change. Run the new unit test in isolation first (`dotnet run --project tests/BlueCode.Tests/...`), then T6 32B × 3 live. Lock in if all green.
4. Run T1 × 32B + T5 × 72B as final canaries.

Each step gets its own atomic commit per CLAUDE.md `{type}({phase}-{plan}): {name}` convention. Suggested phase number: **Phase 10** (next integer after v1.2's 8-9) or **9.1** (decimal-insert via `/gsd:insert-phase` if treating this as urgent v1.2 closure rather than v1.3 work — see §6).

## 6. Phase placement decision

Two viable framings:

**Option A: Phase 9.1 — `/gsd:insert-phase` before milestone close.**

Treats Fixes 1-3 as completing what TOOL-08 promised. Pros: v1.2 ships with the actual T6 fix landed, audit can return to `passed` with a clean conscience, requirement TOOL-08 transitions to fully-validated. Cons: extends v1.2 wall-clock; requires re-audit; risks scope creep if more issues surface.

**Option B: First phase of v1.3.**

Treats Fixes 1-3 as v1.3 work. Pros: respects milestone discipline (v1.2 already declared complete with audit); allows v1.3 to bundle related improvements (ROU-05 escalation, PERF-01 prompt shrink) in a coherent milestone. Cons: v1.2 ships with a known partial fix; v1.1 baseline regression sits unfixed for the duration of v1.3 planning.

**Recommendation:** Option A if the bench validates within 1 hour of starting (the changes are surgical and the bench is the proof). Option B if any of Fixes 1/2/3 turn out to need iteration beyond what's specified here. Default to A unless a complication appears.

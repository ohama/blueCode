<objective>
Add a post-`read_file`-truncated System message injection to the agent loop, mirroring the 09.1-05 `lastEditPath` / `[POST-EDIT CONSTRAINT]` pattern. When the immediately preceding tool result was a `read_file` Success whose header status is `truncated` or `out-of-range`, the NEXT iteration's `buildMessages` output appends a System-role hint guiding the model toward a smaller window or a valid `start_line`. This is the architectural lever PERF-02 needs so Plan 11-02's prompt shrink can DELETE the equivalent base-prompt sentences without regressing T6 or other read-heavy tests.

Purpose: PERF-02 (move contextual hints out of the base prompt). The base prompt currently carries two ~290-char sentences that fire on every LLM call but only matter when a read just returned truncated/out-of-range content. Injecting them post-tool-result instead of preprompt-burning them is what makes Plan 11-02's ≤800-char target reachable without losing behavioral quality on T6 and read-heavy fixtures.

Output: A `lastReadHint` parameter threaded through `runLoop` (parallel to the existing `lastEditPath`), a 2-arm pattern match in `buildMessages` that appends one of two `[POST-READ HINT]` System messages, and a new `testCaseAsync` in `AgentLoopTests.fs` proving the injection fires on a truncated header. No `Domain.fs` change. No `FsToolExecutor.fs` change (the truncated/out-of-range header is already in the payload — we parse it post-hoc in `runLoop`).
</objective>

  <name>Task 1: Thread lastReadHint through runLoop and inject [POST-READ HINT] in buildMessages</name>
  <files>src/BlueCode.Core/AgentLoop.fs</files>
  <action>
Mirror the 09.1-05 `lastEditPath` pattern for read_file results. Concretely:

1. **Add a parameter to `buildMessages`**: After the existing `(lastEditPath: string option)` parameter, add `(lastReadHint: (string * string) option)` where the tuple is `(path, status)` — `status` is one of `"truncated"` or `"out-of-range"`. (Two-string tuple keeps Domain.fs untouched, parallel to the `string option` used for lastEditPath.)

2. **Extend `buildMessages`'s tail**: The existing function ends with:
   ```fsharp
   match lastEditPath with
   | Some path -> baseMsgs @ [ constraintMsg ]
   | None -> baseMsgs
   ```
   Replace with a sequence that appends BOTH messages when both are `Some` (independent — read hint is about the LAST read; edit constraint is about the LAST edit; in practice they can't both be Some on the same iteration because either the previous tool was a read or it was an edit, not both, but compose them defensively):

   ```fsharp
   let withEdit =
       match lastEditPath with
       | Some path -> baseMsgs @ [ <existing constraintMsg> ]
       | None -> baseMsgs
   match lastReadHint with
   | Some (path, "truncated") ->
       withEdit @ [
           { Role = System
             Content =
               sprintf "[POST-READ HINT] The previous read_file on %s returned truncated content (clipped to 2000 chars). Pick a smaller window — set end_line - start_line < 50 — and read again to get unclipped content." path }
       ]
   | Some (path, "out-of-range") ->
       withEdit @ [
           { Role = System
             Content =
               sprintf "[POST-READ HINT] The previous read_file on %s returned out-of-range (start_line > total_lines). The header reported total_lines; choose a start_line <= total_lines and read again." path }
       ]
   | _ -> withEdit
   ```

3. **Add a parameter to `runLoop`**: After `(lastEditPath: string option)` add `(lastReadHint: (string * string) option)`. Pass it to `buildMessages` on the line `let messages = buildMessages config.SystemPrompt userInput history lastEditPath lastReadHint`.

4. **Compute `lastReadHint'` for the recursive call**: Inside the `Ok tr -> ...` branch, alongside the existing `lastEditPath'` computation, add:
   ```fsharp
   let lastReadHint' =
       match tool, tr with
       | ReadFile (FilePath p, _), Success payload ->
           // payload starts with "[file: <path>, lines X-Y of Z, <status>]\n..."
           // Cheapest reliable check: substring search on the FIRST line only.
           let firstLine =
               let nl = payload.IndexOf('\n')
               if nl > 0 then payload.Substring(0, nl) else payload
           if firstLine.Contains(", truncated]") then Some (p, "truncated")
           elif firstLine.Contains(", out-of-range]") then Some (p, "out-of-range")
           else None
       | _ -> None
   ```
   Use `", truncated]"` and `", out-of-range]"` (with the leading comma+space and trailing `]`) so we only match the header status field, NOT a coincidental substring inside the file content. The header format is fixed by `FsToolExecutor.readFileImpl`: `"[file: %s, lines %d-%d of %d, %s]"` where `%s` is one of `not-truncated|truncated|out-of-range`.

5. **Pass `lastReadHint'` in the recursive call**: Update `return! runLoop config model client tools userInput ctx' guard' (loopN + 1) steps' lastEditPath' lastReadHint' onStep ct`.

6. **Update `runSession`**: Pass `None` as the initial `lastReadHint` on the first call: `runLoop config model client tools userInput ctx guard 0 [] None None onStep ct` (the second `None` is the new lastReadHint slot).

7. **Update doc comments**:
   - Add a sentence above `runLoop` mirroring the existing lastEditPath comment: `/// lastReadHint: Some (path, status) when the immediately preceding step was a read_file whose Success header reported "truncated" or "out-of-range"; None otherwise. Used by buildMessages to inject a post-read hint message (Plan 11-01, extending 09.1-05's loop-injection primitive).`
   - Update buildMessages's existing block comment to also mention the read-hint arm.

The new test mirrors the structure of the existing "post-edit_file injection" test (same `recordingLlm` pattern, same `Expect.stringContains` assertion). Concretely:

```fsharp
testCaseAsync "post-read_file injection: truncated header triggers [POST-READ HINT] on next call"
<| async {
    let captured = System.Collections.Generic.List<Message list>()

    let scriptedReplies =
        [ makeMockResponse "reading"
              (toolCall "read_file" "{\"path\":\"big.fs\"}")
          makeMockResponse "done" (FinalAnswer "ok") ]
    let queue = System.Collections.Generic.Queue<_>(scriptedReplies)

    let recordingLlm : ILlmClient =
        { new ILlmClient with
            member _.CompleteAsync messages _model _ct =
                captured.Add(messages)
                Task.FromResult(queue.Dequeue()) }

    // Tool executor: return a Success payload whose first line carries the
    // ", truncated]" status — same format FsToolExecutor.readFileImpl emits.
    let truncatedTools : IToolExecutor =
        { new IToolExecutor with
            member _.ExecuteAsync _tool _ct =
                let payload = "[file: big.fs, lines 1-100 of 100, truncated]\nfile contents go here ..."
                Task.FromResult(Ok (Success payload)) }

    let! result =
        runSession testConfig recordingLlm truncatedTools discardStep "read big.fs" CancellationToken.None
        |> Async.AwaitTask

    match result with
    | Error e -> failtestf "expected Ok, got Error %A" e
    | Ok _ ->
        Expect.equal captured.Count 2 "should be exactly 2 LLM calls (read + final)"
        let secondCallText =
            captured.[1]
            |> List.map (fun m -> m.Content)
            |> String.concat "\n"
        Expect.stringContains secondCallText "[POST-READ HINT]"
            "second LLM call must contain the post-read injection marker"
        Expect.stringContains secondCallText "big.fs"
            "second LLM call must reference the read path"
        // Negative check: first call must NOT contain the marker
        let firstCallText =
            captured.[0]
            |> List.map (fun m -> m.Content)
            |> String.concat "\n"
        Expect.isFalse (firstCallText.Contains("[POST-READ HINT]"))
            "first LLM call (no prior read) must not contain the marker"
}
```

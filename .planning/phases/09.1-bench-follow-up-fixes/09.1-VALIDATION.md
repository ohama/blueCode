## Infrastructure Issue During Run

The bench harness assumed `bench-fixtures/` directory existed at `/Users/ohama/projs/blueCode/bench-fixtures/`.
This directory was absent (it was created during the original v1.2 bench and later cleaned up or never committed).
The initial W1 and W2 runs failed because `cat > bench-fixtures/bug_lastchar.fs` silently failed.

**Resolution:** Created `bench-fixtures/` directory and re-ran W1 and W2 manually:
```bash
mkdir -p /Users/ohama/projs/blueCode/bench-fixtures
# restore W1 fixture, run
dotnet run --project src/BlueCode.Cli -- --verbose --model 32b "Read bench-fixtures/bug_lastchar.fs and fix the bug. Save the corrected version using write_file." 2>&1 | tee /tmp/bench-v1.2-fixed/v9_1_W1_32b.log
# restore W2 fixture, run
dotnet run --project src/BlueCode.Cli -- --verbose --model 32b "Read bench-fixtures/bug_average.fs and add a new function averageSafe that returns int option (None for empty list). Save the updated file." 2>&1 | tee /tmp/bench-v1.2-fixed/v9_1_W2_32b.log
```

This is a bench harness infrastructure issue, not a code regression. The run.sh `v9_1` function was updated
to create `bench-fixtures/` via the heredoc, but the directory itself didn't exist. All 10 final logs are
valid and contain the correct run data.

## Conclusion

**Gates NOT fully met — escalation needed.**

T6 gates (both 32B and 72B) are fully green. Fix 1 (dispatcher partial-bounds) and Fix 2 (truncated
system-prompt hint) together resolved the primary audit failures.

W1 and W2 step-count gates failed: Fix 3 (`edit_file is terminal`) system prompt hint was insufficient
to eliminate the redundant write step in 32B. Two distinct failure modes observed:
- W1: model ignored the hint and explicitly wrote the file (`"I will save the corrected version"`)
- W2: hint was acknowledged (no write_file) but a verification read was substituted, keeping step count at 4

**Recommended next step: Plan 09.1-04** — iterate Fix 3 wording to be more directive. Possible approaches:
1. Stronger wording: `"edit_file is the ONLY action needed to save changes. NEVER call write_file after edit_file."`
2. Add an explicit negative example in the system prompt
3. Reframe as a constraint rather than a note

T1 canary WARN does not block escalation — the behavioral change (1→3 steps on a math question) is
likely model variance rather than a system prompt regression. Monitor in Plan 09.1-04 validation.

**Phase 9.1 status: T6 primary goals achieved; Fix 3 W1/W2 gate failed. NOT ready for /gsd:verify-work
until Plan 09.1-04 resolves W1/W2 step-count gates.**

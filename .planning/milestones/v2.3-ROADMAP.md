## Overview

v2.3 was the second **data-driven** milestone, scoped from v2.2 audit's CORR-EVAL-02 FAIL constraint discovery #2 (persistent extraction bias on shared-prefix function names — `add`/`add3` shared prefix where the model renamed `add3→sum3` but ignored `add→sum`, identical step-5 thoughts across two different READMEs). Goal: resolve the bias via multi-prong intervention (P1 system prompt enumeration directive + P2 few-shot multi-file examples + P3 plan-mode pre-flight rename-target enumeration); verify by re-running CORR-EVAL-02 to PASS (orphan_count=0); flip Correctness 31/40 → 36/40; aggregate verdict 87/100 → 92/100 KEEP.

Outcome: All 6 requirements delivered; CORR-EVAL-02 PASS empirically (orphan_count=0; RUN_TS=20260429-105907); eval doc verdict 87 → 92/100; bench gate 7/7 PASS preserved throughout. The path was **non-linear**: original 3-phase plan (24, 25, 26) hit a structural bottleneck at Phase 26 — the prongs were architecturally scoped to plan-mode while the eval harness uses agent-loop. Phase 27 was added mid-flight to close this gap by migrating P1 from `planSystemPromptSuffix` to `defaultSystemPrompt` with byte-invariant char count (1968 = 1968).

The non-linearity is the milestone's signature lesson: an intervention's reach depends on which code path it lives in. Phase 26 stays in the archive as historical BLOCKED record (commit `7837ad5`) — it's not a failure, it's the diagnostic that informed Phase 27's design.

## Constraint Discoveries This Milestone

- **CORR-EVAL-02 architectural scope mismatch (Phase 26 diagnostic):** Multi-prong intervention scoped to plan-mode could not reach an agent-loop eval. Resolved by Phase 27's P1 migration to `defaultSystemPrompt`. Repo lesson: **for each intervention, explicitly check which code paths exercise it and which paths bypass it**.
- **KV cache contamination is real (Phase 26 Diagnostic D):** Long-running 122B service accumulates contamination that produces hallucination failure modes (e.g., reading "rename" task as "add subtract function"). `launchctl kickstart -k gui/501/com.ohama.qwen122b` clears it. Now mandatory pre-flight for evaluation runs.
- **Char count invariants are powerful audit tools (Phase 27):** The combined plan-mode prompt char count (defaultSystemPrompt + "\n\n" + planSystemPromptSuffix) was provably invariant before/after migration (1968 = 1968). When designing prompt changes, look for transformations that conserve a measurable quantity.

## Plan-Mode vs Agent-Loop Distinction (load-bearing post-v2.3)

This milestone made the plan-mode/agent-loop distinction load-bearing repo knowledge:

- **`defaultSystemPrompt`** (CompositionRoot.fs:68-83+) — sent for ALL invocations (agent-loop AND plan-mode); now includes the P1 enumeration directive (post-Phase-27)
- **`planSystemPromptSuffix`** (CompositionRoot.fs:93-104+) — sent ONLY when `--plan` flag is used; concatenated as `defaultSystemPrompt + "\n\n" + planSystemPromptSuffix`; contains the P2 few-shot example (Example/Targets/Steps block)
- **`PlanValidator.checkRenameTargetsEnumerated`** — runs ONLY in `runPlanTurn` (plan-mode entry); not active in agent-loop

Future prompt or validator changes must explicitly state which mode(s) they target. Bench gate fixtures use agent-loop (no `--plan`); CORR-EVAL-02 eval harness uses agent-loop (no `--plan`).

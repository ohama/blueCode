## E2E User Flow (1/1)

The single critical flow for this CLI:

```
blueCode "<user prompt>"
  → Argu parsing (Cli)
  → CompositionRoot.bootstrap (sync, no network)
  → runSession (Core)
  → runLoop
    → callLlmWithRetry → parseLlmResponse (validates against 8-action enum)
    → dispatchTool actionName toolInput (8-arm match → Tool DU)
    → tools.ExecuteAsync tool ct (FsToolExecutor.create's 7-case match → real impl)
    → ToolResult → Step → onStep → recurse (≤5 iterations)
  → final output
```

Every new tool from v1.2 (edit_file, glob_search, grep_search, read_file-with-header) flows through this loop without any change to `runLoop`, `Step`, or `runSession`. Verified via test suite (236 baseline tests still pass — no regression in routing/loop/tooling) plus integration checker's empty-Core-diff confirmation.

### Bench-discovered tech debt (REVISION — 2026-04-25, post-audit)

After the initial `passed` verdict, a full live bench (Part 3 of [`documentation/benchmark-32b-vs-72b.md`](../documentation/benchmark-32b-vs-72b.md), 36 runs reproducing the v1.1 baseline) exposed two TOOL-08 effectiveness gaps and one TLX-01 mental-model gap. These are real and reproducible (3/3 deterministic on each), but they are **behavioral shortfalls** — the implementation matches its spec, the unit tests assert the spec correctly, the integration check is clean. The audit's structural verdict remains valid; what shifted is the *measured real-world value* of the v1.2 features.

**Item 1 — TOOL-08 dispatcher gap (Phase 9):**

[`AgentLoop.fs:69-72`](../src/BlueCode.Core/AgentLoop.fs#L69-L72) constructs `lineRange = Some(s, e)` only when **both** `start_line` and `end_line` are present. When LLM sends only `start_line` (the exact pattern that motivated TOOL-08 — Part 1 v1.1 32B sent `start_line=2001/4001/6001`), `lineRange = None` and the `out-of-range` branch in [`FsToolExecutor.fs:147`](../src/BlueCode.Cli/Adapters/FsToolExecutor.fs#L147) never fires. Bench T6 32B re-test: 0/4 pass — same outcome as v1.1, just different failure mode (LoopGuard at step 3 instead of MaxLoops at step 5). The unit tests in `FileToolsTests.fs:211-235` exercise the out-of-range branch only with both bounds (`ReadFile(FilePath "small.txt", Some(100, 200))`), so they pass while the actual scenario is unreachable.

This means TOOL-08's **primary motivating use case** (T6 benchmark, REQUIREMENTS.md "근거: 32B 가 결정론적으로 실패 — start_line=2001 …") is NOT measurably resolved despite the requirement being marked Complete. The header is correct when invoked with both bounds; the bridge from "LLM sends start_line alone" to "header fires" is missing.

**Item 2 — TOOL-08 keyword regression on 72B (Phase 9):**

The new header word `truncated` is interpreted by 72B as "the response was clipped; request the full content" — leading to a loop where 72B retries `start_line=1, end_line=179` (full file) repeatedly, getting the same truncated payload each time. v1.1 had no header; 72B inferred from response *size differences* (`2047 chars` vs `1823 chars`) that smaller windows worked, and succeeded in 4 steps. v1.2's header overrides that heuristic. Bench T6 72B: 4/4 PASS (v1.1) → 0/4 FAIL (v1.2). This is a true capability regression introduced by Phase 9's spec choice (`not-truncated|truncated|out-of-range` enum), not by an implementation bug.

**Item 3 — 32B redundant edit_file + write_file pattern (Phase 8):**

In W1 and W2 bench, 32B uses `edit_file` (the new TLX-01 tool) correctly, then immediately follows with `write_file` containing the full file content. The result is correct (idempotent) but wastes a ~1024-token content generation per write. System prompt does not communicate that `edit_file` already persists. Affects performance not correctness; visible in `/tmp/bench-v1.2/pC_W1_32b.log` step 3.

### Pattern observed but NOT v1.2-attributable

- **B2 (divide-by-zero) regression on both models** (v1.1 ✓ → v1.2 ✗): Same fixture, same prompt, but both models now flag "integer truncation" instead of "empty list → DivideByZeroException". Most likely caused by Phase 8's expansion of the system prompt (5 → 8 actions, ~2x growth) shifting LLM attention. Not an implementation defect of any specific phase. Surfaces as concrete motivation for **PERF-01** (system prompt shrink) which was previously a speculative deferred item.
- **32B mlx_lm.server hang on W2 first attempt**: Cleared by `launchctl kickstart -k`. Same class as the v1.0 OPS-01 prompt-cache concerns. Not v1.2-related.

## Verdict

**Initial (2026-04-25T13:00Z):** `passed` — based on phase verifications (5/5 each), integration check (9/9), test suite (240/240), zero anti-patterns, Core purity intact.

**Revised (2026-04-25T13:55Z):** `tech_debt` — initial verdict stands for **structural** correctness (the milestone delivered what each spec said), but a same-day live bench (Part 3 of [`documentation/benchmark-32b-vs-72b.md`](../documentation/benchmark-32b-vs-72b.md), 36 runs reproducing the v1.1 baseline) showed TOOL-08's primary motivating scenario (T6 32B `start_line`-only requests) is NOT actually resolved due to a dispatcher gap, and 72B's previously-passing T6 path now fails 4/4 due to the new `truncated` header keyword. These are tech debt — not blockers — because:

1. The phase deliverables match their specs verbatim (header format, schema enum, executor impls). Unit tests correctly assert the spec.
2. The shortcomings are *bridge* and *semantics* gaps, fixable in a v1.3 phase without rolling back v1.2 code.
3. v1.0/v1.1 baseline behavior is preserved or improved on most tests (T3 32B count, T5 72B `glob_search` adoption, T7 32B depth, W1/W2 correctness).
4. Combined accuracy 32B 13/15 (87%), 72B 12/15 (80%) excluding B3 N/A — comparable to v1.0 daily-driver acceptance threshold.

**Recommended next action:** `/gsd:complete-milestone 1.2` to ship and tag, then immediately scope a small v1.3 milestone whose first phase addresses the three bench-discovered items in `tech_debt[]`. The shipping stance is *honest*: v1.2 added tools that work in their own right, but the read_file metadata feature requires a follow-up to deliver its motivating value.

**Why not `gaps_found`:** A `gaps_found` verdict would block milestone completion to plan gap-closure phases. Doing that here would conflate two different things: (a) the spec-vs-implementation contract (intact) and (b) the requirement-intent-vs-real-behavior contract (partial). The first is the audit's traditional concern; the second is more honestly a v1.3 input than a v1.2 blocker. Forcing them into the same milestone risks freezing v1.2's deliverables (which other v1.3 work would build on) while we redesign the dispatcher.

**v1.3 candidate phases (seed for `/gsd:new-milestone`):**

1. **HIGH** — Read-file dispatcher fix: `start_line` alone fills `Some(s, s+100)` so `out-of-range` fires for the actual T6 prompt; system prompt clarifies `truncated` semantics. (closes Item 1 + Item 2)
2. **HIGH** — System-prompt hint that `edit_file` does not need a follow-up `write_file`. (closes Item 3)
3. **MEDIUM** — ROU-05 auto-escalation on `MaxLoopsExceeded` / `LoopGuardTripped` (newly motivated by 72B regression rather than just being a hedge).
4. **MEDIUM** — PERF-01 system prompt length research, with B2 regression as a concrete behavioral signal to validate against.

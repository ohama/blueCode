<objective>
Close the W1 × 32B SC4 step-count gate (4→3) that wording-only intervention could not close in Plan 09.1-04. Use a code-level loop-injection: after a successful `edit_file`, the agent loop appends a synthetic constraint message (after the user prompt) for the next LLM call. The constraint blocks the model from choosing `write_file` or a same-path verification `read_file`, regardless of what the user prompt asked for.

Purpose: The Plan 09.1-04 SUMMARY established that no system-prompt wording can override an explicit user-prompt tool instruction (`"using write_file"`). Output: A loop-injection mechanism in `AgentLoop.fs`, a reapplied W2-effective directive in `CompositionRoot.fs` (defense-in-depth), a new unit test asserting the injection reaches the second LLM call, and a re-revalidation section in `09.1-VALIDATION.md` documenting the W1+W2+T1 bench evidence at `/tmp/bench-v1.2-fixed-rev2/`.

<decision>
**Option A (loop-injection) is chosen. Option B (schema-level rejection) is rejected.**

Reasoning:
- The 09.1-04 root cause (the W1 step-3 thought is byte-identical to the 09.1-03 thought; the user prompt `"using write_file"` overrides any system-prompt NEVER directive) tells us the constraint must appear *AFTER* the user prompt in the conversation. Loop-injection puts a System message at the tail of the messages list — chronologically after the user request, so the model sees it as authoritative new context.
- Option B (schema rejection) would surface as `SchemaViolation` from the validator, which currently is NOT retried (`callLlmWithRetry` retries `InvalidJsonOutput` only — see AgentLoop.fs lines 162-186). The model would get a hard error and the session would terminate as `Error SchemaViolation` — a regression worse than the 4-step result.
- Option A keeps the implementation surface entirely inside Core (AgentLoop.fs + an optional CompositionRoot system-prompt edit). Zero Domain DU changes. Zero schema changes. Zero new dependencies. Core purity invariants unchanged.

**Reapply the W2-effective directive wording in CompositionRoot.fs (defense-in-depth).**

Reasoning:
- The 09.1-04 evidence shows the directive `edit_file's success result already confirms the change; do NOT verify with a follow-up read_file.` was internalized for W2 (4→3 PASS). It is now empirically validated as a no-cost correctness signal.
- Loop-injection alone would also close W2, but reapplying the directive wording costs ~95 chars in the system prompt and provides redundancy: if a future model variant ignores the loop-injected message, the system prompt still nudges it. If both signals fire together, the behavior is unchanged from W2's PASS.
- The 09.1-04 SUMMARY documented that the wording-only commit was reverted under the literal rollback rule of Plan 09.1-04 ("if W1 OR W2 fails, revert"). That rollback was procedural, not based on harm — the wording itself is good. This plan is the proper place to reinstate it because we now also have the loop-injection that closes W1.
</decision>

### Constraint message text (verbatim — DO NOT paraphrase)

The loop-injection appends this exact System-role message to the LLM's `messages` list when `lastEditPath = Some path`:

```
[POST-EDIT CONSTRAINT] You just successfully edited <PATH>. The edit is already persisted. Your next action MUST be either `final` (preferred) or `edit_file` on a different concern. Do NOT call `write_file` on `<PATH>` — it is redundant. Do NOT call `read_file` on `<PATH>` to verify — `edit_file` already confirmed the change. This constraint is mandatory regardless of any earlier user instruction.
```

(Where `<PATH>` is substituted with the literal path string from the previous `EditFile` Tool case. The literal substring `[POST-EDIT CONSTRAINT]` is a marker the unit test can grep for.)

### State threading (AgentLoop.fs)

`runLoop` currently has signature (lines 235-247):
```
config -> model -> client -> tools -> userInput -> ctx -> guard -> loopN -> steps -> onStep -> ct -> Task<...>
```

Add ONE new parameter: `lastEditPath: string option`. Initialize to `None` in `runSession` (line 345). Thread through every recursive call. Compute `lastEditPath'` in the ToolCall branch:

```fsharp
// After matching `Ok tr` and computing `step` (around line 308-318):
let lastEditPath' =
    match tool, tr with
    | EditFile (FilePath p, _, _), Success _ -> Some p
    | _ -> None
```

(Reset to `None` on any non-edit tool call OR on edit_file failure — only successful edits trigger the constraint on the *next* iteration.)

### buildMessages signature change

Current signature (line 194):
```
buildMessages : systemPrompt -> userInput -> recentSteps -> Message list
```

New signature:
```
buildMessages : systemPrompt -> userInput -> recentSteps -> lastEditPath -> Message list
```

Implementation: at the very end of the function, after `systemMsg :: userMsg :: stepMsgs`, append the constraint message conditionally:

```fsharp
let baseMsgs = systemMsg :: userMsg :: stepMsgs
match lastEditPath with
| Some path ->
    let constraintMsg =
        { Role = System
          Content =
            sprintf
                "[POST-EDIT CONSTRAINT] You just successfully edited %s. The edit is already persisted. Your next action MUST be either `final` (preferred) or `edit_file` on a different concern. Do NOT call `write_file` on `%s` — it is redundant. Do NOT call `read_file` on `%s` to verify — `edit_file` already confirmed the change. This constraint is mandatory regardless of any earlier user instruction."
                path path path }
    baseMsgs @ [ constraintMsg ]
| None -> baseMsgs
```

(Trailing System message — Qwen's Instruct chat template treats this as authoritative new directive that post-dates the user turn. This is the architectural lever that beats user-prompt priority.)

### Pattern 1: Dispatcher line-range completion (Fix 1)

**What:** Extend `dispatchTool`'s `match startL, endL with` to fill missing bounds with conservative defaults so `readFileImpl` always receives a `Some(s, e)` when the LLM provided at least one bound.

**When to use:** Phase 9.1 implementation site — exact diff in `documentation/v1.2-bench-followup.md` §2 Fix 1.

**Verified location (2026-04-25 against repo HEAD):**

```fsharp
// src/BlueCode.Core/AgentLoop.fs lines 69-72 — VERIFIED EXACT MATCH:
let lineRange =
    match startL, endL with
    | Some s, Some e when s > 0 && e >= s -> Some(s, e)
    | _ -> None
```

**Diff to apply (from followup doc §2, copy verbatim):**

```diff
 let lineRange =
     match startL, endL with
     | Some s, Some e when s > 0 && e >= s -> Some(s, e)
+    | Some s, None        when s > 0      -> Some(s, s + 99)   // 100-line window
+    | None,   Some e      when e > 0      -> Some(1, e)        // bounded read from start
     | _ -> None
```

**F#-specific notes the followup doc didn't enumerate:**

1. **Pattern-match exhaustiveness:** F# compiler accepts the new arms because the wildcard `| _ -> None` covers all remaining cases (incl. `None, None` and out-of-guard cases like negative `s`). No exhaustiveness warning will fire. Confirmed by inspection.
2. **Guard ordering:** New arms must appear *before* the wildcard `| _ -> None` (the diff places them correctly between the existing first arm and the wildcard). Reordering would be a silent semantic change.
3. **Integer overflow on `s + 99`:** F# `int` (`System.Int32`) addition wraps silently. If a malicious/buggy LLM emits `start_line: 2147483647` (Int32.MaxValue), `s + 99` wraps to `-2147483550`. The constructed tuple is `Some(2147483647, -2147483550)`. This **safely** falls through `readFileImpl`'s guard `Some(s, e) when not (s >= 1 && e >= s)` (`FsToolExecutor.fs:134`) → "invalid line range" Failure branch. No crash, no out-of-range header — just a graceful failure message. Realistic LLM inputs are 4-digit at most; this is defense-by-accident but worth a one-line comment in the dispatcher arm. *No action required by the planner beyond awareness.*
4. **No async/HttpClient/Spectre concerns:** Fix is in pure Core code, uses only existing primitives (`int option`, tuple construction). CI grep `scripts/check-no-async.sh` is unaffected (no `async {}` introduced). Core purity invariant intact.

### Anti-Patterns to Avoid

- **Adding a new test module for the dispatcher fixture** — would force dual-registration (`.fsproj` + `rootTests`). Four executors have hit this pitfall across v1.0 + v1.1 (CLAUDE.md). The new `testCase` belongs inside the existing `readFileTests` testList in `FileToolsTests.fs`.
- **Using `dotnet test` to run the new fixture** — `dotnet test` does NOT run Expecto in this project (STATE.md decision row, 2026-04-25). Canonical runner: `dotnet run --project tests/BlueCode.Tests/BlueCode.Tests.fsproj` or with filter `-- --filter-test-list "FsToolExecutor.ReadFile"`.
- **Using `Expect.stringContains` on single letters** — header words `truncated`, `lines`, `file` collide with line content. Anchor body assertions with `\n` (STATE.md pattern row). The followup doc fixture already does this correctly (`Expect.isFalse (content.Contains("\na\n"))`).
- **Clamping `endLine` to `totalLines` in the out-of-range branch** — STATE.md decision (2026-04-25): "Out-of-range branch preserves the RAW requested `endLine` (no clamp) so the bounds-violation signal is unambiguous to the LLM". The followup doc test asserts `lines 2001-2100 of 3` — the `2100` is the raw post-default-window value, not clamped. This is intentional. Don't try to "fix" it.
- **Re-running all 36 bench cases as validation** — followup doc §4 explicitly says don't. 10 targeted runs is the validation gate.

## Common Pitfalls

### Pitfall 1: Forgetting test discovery requires NO action this time

**What goes wrong:** Reflexive habit from prior phases — "added a new test, must update `.fsproj` + `rootTests`."
**Why it happens:** v1.0 + v1.1 saw four separate executors hit this exact pitfall when adding new test *modules*. The reflex generalizes incorrectly.
**How to avoid:** The new fixture is a `testCase` *inside an existing `testList` inside an existing module*. `FileToolsTests.fs` is already at `BlueCode.Tests.fsproj:12` and `RouterTests.rootTests:97`. No registration changes needed.
**Warning signs:** A planner task that says "add `BlueCode.Tests.DispatcherTests.tests` to RouterTests.fs". STOP — go inside `FileToolsTests.fs:readFileTests` instead.

### Pitfall 2: Followup doc fixture API drift

**What goes wrong:** Copy-pasting `documentation/v1.2-bench-followup.md` §2 Fix 1 lines 62-74 verbatim into `FileToolsTests.fs` results in compilation errors.
**Why it happens:** The doc uses idealized helpers — `use fx = newFixture()`, `fx.Root`, `createExecutor` — that don't exist in the actual codebase. The real helpers are `newFixture () : string`, `create : string -> IToolExecutor`, and there is no IDisposable wrapper.
**How to avoid:** Adapt the fixture body to match the existing `FileToolsTests.fs:211-235` style. Concretely:

```fsharp
testCase "TOOL-08-bench: start_line alone past EOF triggers out-of-range header" <| fun () ->
    let root = newFixture ()
    try
        File.WriteAllText(Path.Combine(root, "small.fs"), "a\nb\nc\n")  // 3 lines
        let exe = create root
        // After Fix 1, dispatcher constructs Some(2001, 2100); test that path directly.
        let result = exec exe (ReadFile(FilePath "small.fs", Some(2001, 2100)))
        match result with
        | Ok(Success content) ->
            Expect.stringContains
                content
                "[file: small.fs, lines 2001-2100 of 3, out-of-range]"
                "out-of-range header preserves raw range"
            // Body must be empty — no file content after header on out-of-range
            Expect.isFalse (content.Contains("\na\n")) "no body content"
            Expect.isFalse (content.Contains("\nb\n")) "no body content"
            Expect.isFalse (content.Contains("\nc\n")) "no body content"
        | other -> failtestf "expected Success, got %A" other
    finally
        cleanup root
```

**Warning signs:** F# compile error `error FS0039: The value or namespace 'createExecutor' is not defined` or `'newFixture' does not return a type with a 'Root' property`.

### Pitfall 3: `dispatchTool` test claim vs. what's actually being tested

**What goes wrong:** The followup doc's "Required test" comment says "*simulates dispatcher output*" — the test invokes `IToolExecutor` with `Some(2001, 2100)` directly, not through `dispatchTool`. A reviewer may flag "this doesn't test Fix 1; it tests `readFileImpl`".
**Why it happens:** True observation — but `readFileImpl` already passed Phase 9 verification with `Some(100, 200)` on a 3-line file. The new test's *role* is to certify that **the dispatcher-output shape that Fix 1 produces** lands the executor in the out-of-range branch. The test's value is in the literal pair `(2001, 2100)` matching what `Some(s, s+99)` builds for `s=2001` — this is the contract the dispatcher is *supposed* to honor.
**How to avoid:** Phrase the test name and assertion comments to make the chain explicit. Suggested wording: `"TOOL-08-bench: dispatcher's Some(s, s+99) output for start_line=2001 reaches out-of-range branch"`. Alternatively, add a sibling test that constructs JSON, calls `dispatchTool` indirectly through `runSession` with a stub `ILlmClient`, and asserts the produced `Tool` value matches `ReadFile(_, Some(2001, 2100))`. The followup doc judged that overkill; agree.
**Warning signs:** Plan task description says "test `dispatchTool` directly" — clarify scope or add the second test.

### Pitfall 4: Bench harness phase-granularity mismatch

**What goes wrong:** §4 says "T6 × 32B × 3", but `/tmp/bench-v1.2/run.sh` only takes `phase1|phaseA|phaseB|phaseC|all` arguments. There is no `T6 32b 3` invocation.
**Why it happens:** The doc author treated the validation list as a logical specification, not a literal command. `phaseA` runs T1 + T6 × 3 for both 32B and 72B (12 runs). To match §4 exactly (10 runs), the planner must either:
1. Run `phaseA` and ignore the T1 results + the 72B side of T1 (wastes ~30s but reuses harness verbatim), then add bespoke single-run invocations for W1 32B / W2 32B / T1 32B (regression canary) / T5 72B (regression canary).
2. Add a small dispatcher arm to `run.sh` (`bench-v1.2-fixed) <three calls> ;;`).
**How to avoid:** Plan a **task** in Plan 9.1-04 (validation) titled "Add `9.1-validation` selector to /tmp/bench-v1.2/run.sh" or accept the `phaseA + ad-hoc` approach. Either is fine; pick one explicitly so the executor doesn't improvise.
**Warning signs:** Validation task says "run `bash /tmp/bench-v1.2/run.sh T6` " — that's not a valid case label; the script will print the usage line and exit 1.

### Pitfall 5: System-prompt char-budget arithmetic

**What goes wrong:** Fix 2 adds ~95 chars; Fix 3 adds ~85 chars. Combined ~180 chars on top of the current ~1280. PERF-01 (deferred to v1.3) wants the prompt at ~600 chars eventually — the audit doc ties B2 regression speculatively to prompt length.
**Why it happens:** Both fixes are necessary for behavioral correctness; PERF-01 is a separate compression effort.
**How to avoid:** Don't sweat it. The followup doc §2 explicitly says "Not material vs. PERF-01's eventual 600-char target." Phase 9.1 prioritizes correctness; PERF-01 will absorb the new lines in its own scope.
**Warning signs:** A planner task that tries to *combine* Fix 2/3 with prompt-shrink work. Refuse — that's PERF-01 scope creep.

### Pitfall 6: 240 → 241 test count claim

**What goes wrong:** Success Criterion 5 says "240 baseline + 1 new = 241". But the baseline reported at audit time was "240 passed, 1 ignored, 0 failed" (audit lines 81, 165). After Fix 1, the count is 241 passing + 1 ignored. Don't accidentally count the ignored test.
**Why it happens:** Easy to miscount when reporting.
**How to avoid:** Final verification command from `dotnet run --project tests/BlueCode.Tests/BlueCode.Tests.fsproj` will print "241 passed, 1 ignored". Match exactly.
**Warning signs:** Verification report says "242 tests" — you've double-counted the ignored smoke test.

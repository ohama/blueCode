# Requirements: blueCode v2.0 Persistence + Planning

**Defined:** 2026-04-26
**Core Value:** Mac 로컬 Qwen 3.5 122B를 strong-typed F# agent loop로 안정적으로 돌린다 (single-model canonical post-Phase-19; switched from 32B/72B in Phase 17 SWITCH; 35B retained as cold rollback)
**Milestone goal:** Break the process-lifetime constraint that v1 deliberately accepted. Bundle cross-turn memory (multi-turn REPL keeps context, `--resume <id>`) with plan-then-execute mode (typed plan DU, user approval gate, schema-validated execution).

## v2.0 Requirements (8 requirements, 2 categories — ALL ✓ COMPLETE)

### Persistence

- [x] **PERSIST-01**: Multi-turn REPL maintains conversation history within a single session ✓ (Phase 15, 2026-04-27)
  - **Outcome:** ✓ Closed. `runSession` extended with `priorSteps: Step list`; REPL threads `Session` across turns; turn 2 sees turn 1's `Step list` as prior context. Verified by mocked-LLM multi-turn test in ReplTests.fs.

- [x] **PERSIST-02**: Session state persists to `~/.bluecode/sessions/<id>.jsonl` between turns ✓ (Phase 15, 2026-04-27)
  - **Outcome:** ✓ Closed. JSONL format: `{"version":2,"sessionId":"...","createdAt":"..."}` header + per-turn `TurnComplete` envelope. Last-envelope-wins on Load. Coexists with v1 per-step crash log at `~/.bluecode/session_<ts>.jsonl`.

- [x] **PERSIST-03**: `--resume <id>` flag loads a prior session and continues from its last step ✓ (Phase 15, 2026-04-27)
  - **Outcome:** ✓ Closed. Argu accepts `--resume <ID>`. Unknown id → exit 1 + `SessionNotFound` on stderr (no stack trace). Corrupt JSONL → exit 1 + `SessionCorrupt`. Verified empirically with live binary smoke + 5 SessionStoreTests round-trip + error-path cases.

- [x] **PERSIST-04**: New sessions get a fresh id automatically; `--new-session` forces fresh ✓ (Phase 15, 2026-04-27)
  - **Outcome:** ✓ Closed. Argu accepts `--new-session` (with `--newsession` AltCommandLine alias). `--resume X --new-session` rejected at startup (post-parse validation, before bootstrap) with exit 2 and "conflicting flags" stderr message. Session id printed to stderr at startup (grep-able).

### Planning

- [x] **PLAN-01**: Agent loop supports a `Plan` DU as a new `LlmOutput` variant ✓ (Phase 14 DU, 2026-04-26; JSON parse Phase 16, 2026-04-27)
  - **Outcome:** ✓ Closed. `Domain.LlmOutput` extended with `Plan of Plan` where `Plan = { Steps: PlannedStep list; Rationale: string }` and `PlannedStep = { Tool: ToolName; Input: ToolInput; Rationale: string }`. JSON parse layer in Json.fs `llmStepSchema "plan"` enum + `toLlmOutput` Plan branch handles schema-invalid → `PlanInvalid "schema-invalid: ..."` (4th PlanInvalid mode beyond Phase 14's 3 structural rules).

- [x] **PLAN-02**: `--plan` CLI flag enables plan-then-execute mode for the next turn ✓ (Phase 16, 2026-04-27)
  - **Outcome:** ✓ Closed. Argu accepts `--plan` (boolean). `planSystemPromptSuffix` (with `OVERRIDE — PLAN MODE ACTIVE` preamble auto-added during 16-02 execution to make 122B comply) instructs LLM to emit a plan before any tool call. `--plan` + `--resume <id>` is allowed (resume into plan mode for next turn). `--plan` without prompt → exit 2 ("v2.1+ scope"); `--plan --with-35b` → exit 2 (35B is rollback only).

- [x] **PLAN-03**: User approval gate (a/r/e/q) between plan emission and execution ✓ (Phase 16, 2026-04-27)
  - **Outcome:** ✓ Closed. PlanGate.fs renders Spectre numbered table (step #, tool, input preview, rationale); `IKeyReader` port abstraction enables testable keystroke dispatch (`realKeyReader` uses `Console.ReadKey(intercept=true)` with stdin-redirect fallback for piped smoke tests); a/r/e/q dispatch returns `PlanGateDecision`; on Reject, agent loop reruns turn with `[PLAN REJECTED]` Role=User injection.

- [x] **PLAN-04**: Plan validation runs BEFORE user sees approval prompt ✓ (Phase 14 validator + Phase 16 wiring, 2026-04-27)
  - **Outcome:** ✓ Closed. Pure `validatePlan : Plan -> Result<Plan, AgentError>` in `src/BlueCode.Core/PlanValidator.fs` (Phase 14): 3 structural rules (length ≤ 5, unknown tool name, duplicate adjacent steps). Phase 16 wires the 4th `PlanInvalid` failure mode (schema-invalid input) at JSON parse time before the validator runs. Total 2 attempts (1 initial + 1 retry) on either parse-time or validator-time PlanInvalid; surfaces error after 2nd failure.

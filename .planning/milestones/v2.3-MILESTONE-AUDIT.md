## Tech Debt Inventory

### Phase 27: harness modification

**Item:** `bench/eval-qwen35-122b.sh` modified in commit `9f8e06e` — `|| true` guard on `grep -cE` in PASS path + tee verdict line to `$out`.

**Why:** Under `set -euo pipefail`, `grep -cE` exits 1 on zero-match (which is the SUCCESS case for orphan count check). This caused the harness to abort before writing `refactor_orphan_count.txt`. The fix was applied per Rule 3 (auto-fix blockers) during Phase 27-02 execution because the success path could not report success otherwise.

**Conflict:** ROADMAP §Phase 27 listed "do not modify `bench/run.sh` body or `bench/eval-qwen35-122b.sh` body" as out-of-scope guardrail. The auto-fix overrode this guardrail per the documented deviation rules.

**Status:** Documented in 27-02-SUMMARY.md, 27-VERIFICATION.md, and this audit. Single 5-line change; isolated; tested by the very PASS run that produced orphan_count=0.

**Action:** None required. Future eval harness changes should ride formal phases per the original guardrail intent.

### Phase 26: BLOCKED record preservation

## Lessons (for future milestones)

1. **Architectural scope mismatch is a recurring class of bug.** v2.3 is the second milestone where an intervention's reach was misjudged at scoping time (v2.2 ceiling raise was necessary-but-insufficient; v2.3 prongs were plan-mode-scoped while eval is agent-loop). Future scoping should explicitly check: *"For each intervention, which code paths exercise it? Which paths bypass it? Does the test/eval that proves the intervention works actually run through it?"*

2. **The plan-mode vs agent-loop distinction is now load-bearing.** `defaultSystemPrompt` is for both modes; `planSystemPromptSuffix` is plan-mode-only. Future prompt changes should explicitly state which mode(s) they target.

3. **KV cache contamination is real.** `launchctl kickstart` should be a documented pre-flight for any eval that depends on fresh model state. Phase 26 Diagnostic D and Phase 27-02 both demonstrated this empirically.

4. **Mid-milestone replan via `/gsd:add-phase` works.** v2.3 added Phase 27 mid-flight after Phase 26 BLOCKED. The roadmap supersession pattern (preserve old phase as historical, add new phase that takes over requirements) kept the milestone alive without inflating to v2.4.

5. **Char count invariants are powerful.** Phase 27's migration was easy to verify because the combined plan-mode prompt char count was provably invariant (1968 = 1968). When designing prompt changes, look for transformations that conserve a measurable quantity.

6. **`/gsd:audit-milestone` skipping in yolo mode is risky.** Phase 26 BLOCKED was caught by the executor at run-time, not by a verifier. Had the executor been less defensive (skipped the failure_path branch), Phase 26 might have committed bad eval doc edits. The protection came from the plan, not from a separate verifier pass. Future audits should keep this invariant: failure_path blocks in plans are the safety net of last resort.
